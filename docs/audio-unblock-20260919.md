# 点击说话一直显示开启麦克风

## 实机原因

ADB 读取 `qiji_config result`：`busy=1 recording=0`。`ps` 显示 GUI 工作线程等待 `Mutex:147`，持有者是上一次 ADB `qiji_config speak` 测试任务，仍停在播放。日志最后是 `PTT: stopping active TTS to prevent echo`，随后没有打开录音设备的记录。

播放图把 24kHz 单声道 PCM 输入到 48kHz 双声道硬件通道，中间的 volume 滤镜不负责转换，报 `AVERROR_PATCHWELCOME` 后数据不再被消费。PCM 写入没有超时，播放任务一直持有 speak_lock；按说话又无限等待该锁。这是播放故障连带阻塞录音，不是触摸失效。

## 实现

- PCM 发送前将 24kHz / 16kHz 单声道转换成硬件要求的 48kHz 双声道。整数倍率线性插值，跨云端分块保持前一采样；输入输出时长一致，不改硬件时钟，不跳过 FFmpeg 格式检查。
- 媒体 PCM accept 最长等 5 秒，发送 socket 单次等待 250ms；短写保留已写字节并继续，应用总等待限制为每块 5 秒。
- 取消播放只设置原子标志，不在语音状态锁内执行媒体 IPC。写入循环检查标志并退出。
- speak_lock 竞争最长等待 5 秒，超时返回 `-ETIMEDOUT`，UI 显示具体超时提示。
- 媒体控制请求有收发超时；失败的控制连接 shutdown，避免迟到响应被当成下一次请求的结果。关闭失败时保留回调对象，避免悬空引用；这种媒体故障仍可能需要重启。
- 保留单行状态栏、无键盘界面、58px 语音按钮和 R2 ROMFS 构建校验。

## 验证与限制

使用实际 audio_playback.c 的主机测试通过：转换的目标声道与采样数量、跨分块连续性、短写、暂时不可写重试、EOF、错误返回、5秒超时、跨线程取消。另从实际 voice_channel.c 编译语音锁函数，验证竞争超时及释放后重试成功。官方目标板构建与最终镜像校验结果记录在归档中。

将实际媒体客户端 accept / send 函数编译到主机测试，以真实 Unix socket 制造缓冲区背压：验证部分发送不关连接、满缓冲区返回 EAGAIN、读取数据后可继续发送。主机 socket 行为通过，板端 NuttX 的表现仍需烧录验收。

本次仅修复已观察到的播放等待链路；不宣称所有媒体服务调用都能自动恢复。新的固件尚待上板确认录音、识别及发声；主机测试不代表麦克风或扬声器验收。当前板上遗留的旧播放任务无法通过新源码自行恢复，需重启，完整修复需烧入新固件。

通用镜像 `qiji-chat-audio-unblock.img`；本地调试镜像 `qiji-chat-audio-unblock-2f-debug.img` 预置 2F Wi-Fi，不预置云端 Key。
